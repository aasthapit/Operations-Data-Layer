Redis as the fleet state store

A pull-fed read cache replaces Postgres for all collected OpenShift fleet state: compressed section blobs per cluster, purpose-built fleet indexes, and an explicit cache contract.

Section

Context

The data layer collects inventory, configuration and live utilization (metrics.k8s.io) from every OpenShift cluster's API server, computes health, and serves it through a REST API, a dashboard and an MCP server.

Until now the collected state lived in Postgres: current-state tables replaced wholesale per cluster on every sweep, plus an append-only health snapshot table. The hosting environment does not allow Postgres. Redis is the approved store, and the question was whether Redis, keyed as a pull/read cache of OCP metrics and inventory, can carry the whole product, and what changes when the fleet is 900 clusters with hundreds of applications each.

What the store has to serve, taken from the API read paths in data-layer/app/api/:

Read patterns the store must answer
Read patternExamplesPostgres today
Fleet rollups over one row per clusterOverview, health by region, version spread, capacity by groupFull scan of clusters, aggregated in Python
Filtered cluster listsRegion, environment, status, version, teamIndexed WHERE
One cluster, one sectionNodes, namespaces, workloads, pod issues, resources, timelinePer-table WHERE cluster_name = ?
Fleet-wide entity queriesApplications across clusters, expiring certificates, pod issues, quotas, OLM packages, MCPs, routes, events, images, config referencesIndexed table scans plus Python grouping
Joins for impactBlast radius: version / operator / OLM / image, to clusters, to application namespaces, to teamsSeveral queries joined in Python

The write side is simple: one collector process assembles one plain-dict document per cluster and replaces that cluster's rows in a single transaction.

Headline finding

5 GB at 900 clusters versus 21 GB for one key per object.

Section

Decision

Redis becomes the only store for collected fleet state, designed as a pull-fed read cache with three kinds of keys. The full contract is docs/redis-keyspace.md.

  • Per-cluster keys under one hash tag {c:<name>}: a summary HASH (the former clusters row), ten compressed section blobs (operators, nodes, namespaces, workloads, images, refs, pod issues, resources, resource status, health checks), a snapshots ZSET for history, and a ledger.
  • Fleet indexes under {fleet}: SETs per cluster dimension, per-operator HASHes, a namespace HASH with team / app / class SETs and usage ZSETs, per-kind resource HASHes with status SETs for the kinds that are queried fleet-wide, a certificate-expiry ZSET, image refcounts and usage SETs, and reference SETs.
  • Runs: a LIST of sweeps and the last-run pointer.

Write protocol, one cluster

The write protocol replaces one cluster atomically in a single MULTI/EXEC:

  1. Reverse the cluster's previous fleet contributions from its ledger.
  2. Write summary, sections and snapshot.
  3. Add the new fleet contributions.
  4. Write the new ledger.

The read side never scans every cluster's detail to answer a fleet question; the fleet indexes exist precisely for the questions the product asks.

Cache semantics

  • Pull, not push. The collector pulls on REFRESH_INTERVAL_SECONDS and on demand (POST /api/refresh for the fleet, POST /api/clusters/{name}/refresh for one cluster behind a single-flight lock).
  • Freshness is visible. Every summary carries last_synced, age_seconds and stale; the API never hides that it is serving a cache.
  • Expire, never evict. Per-cluster keys carry REDIS_TTL_SECONDS (default 24 h) so a cluster that is never collected again disappears. The Redis instance runs maxmemory-policy noeviction, because a cache that silently drops one cluster would answer blast-radius questions wrongly.
  • Restart without a storm. RDB snapshots (or AOF) stay on, so an API restart serves the last picture immediately instead of forcing a full re-collection. The cache is rebuildable, but at 900 clusters rebuilding takes minutes and hammers the fleet.

Section

Options considered

Four keyspace designs
OptionSummaryWhy not, or why
A. One key per object Mirror the ORM: every namespace, workload and resource as its own HASH; index SETs for every column that was indexed in Postgres. About 20 GB at 900 clusters versus about 5 GB, from per-key overhead and member strings. Millions of keys, and a write of one cluster becomes tens of thousands of commands. No benefit: the API never reads one object by id.
B. RedisJSON + RediSearch Redis Stack or Enterprise: documents as JSON, declarative secondary indexes, FT.SEARCH and FT.AGGREGATE. Attractive: removes hand-built indexes and adds full-text search. Rejected as the baseline because the modules are not available on every managed Redis (AWS ElastiCache, classic Azure Cache for Redis, GCP Memorystore), it still cannot join, and memory grows about 1.5 to 2x. Kept as an optional accelerator.
C. One blob per cluster One compressed blob per cluster, no fleet indexes. The simplest possible keyspace. Every fleet question decompresses every cluster: 900 x about 1.3 MB per request. Fine at 10 clusters, unusable at 900.
D. Sections + indexes (chosen) Per-cluster detail as compressed sections; fleet-wide questions from purpose-built indexes maintained through per-cluster ledgers. Reads are one or two round trips; writes are one transaction per cluster; memory is dominated by compressed detail; works on plain Redis 7 (OSS, ElastiCache, Azure, Memorystore, Enterprise).

Plain Redis 7 core with no modules is the compatibility floor. Nothing in the design needs Lua, modules or keyspace notifications.

Sizing

Measured on the local kind fleet (5 clusters, tiny): a sweep takes about 450 ms, a cluster document is about 250 resources / 17 namespaces / 16 workloads, and the whole Postgres database was 13 MB.

The model below assumes a production cluster with 250 application namespaces (about 1,700 workloads, about 16,600 inventory objects, about 26,000 rows in total), a JSON row of about 450 B, and 8x zlib compression on the sections (measured 8 to 12x on this kind of JSON).

Sizing model at 10, 100 and 900 clusters
Clusters Sections + summaries + history Fleet indexes Total (logical) With 25% fragmentation One key per object
1014 MB31 MB45 MB0.06 GB0.23 GB
1000.14 GB0.31 GB0.45 GB0.56 GB2.4 GB
9001.29 GB2.75 GB4.0 GB5.1 GB21 GB

Where the fleet indexes go at 900 clusters: resource hashes for fleet-queried kinds 1.2 GB (routes, PVCs, PVs, quotas and events dominate), config references 0.9 GB, image usages 0.25 GB, namespaces 0.21 GB, certificates 0.19 GB, everything else under 50 MB.

Two knobs keep this honest: the reference index is optional (REDIS_INDEX_REFS, falling back to per-cluster sections when a cluster filter is given), and the large fleet hashes must be read with HSCAN and paginated endpoints rather than HGETALL (ADR-0003).

Measured afterwards on a synthetic 900-cluster load (ADR-0003, docs/adr/synthetic-load-900.md): 4.79 GB used memory, 54,508 keys, 1.31 MB per cluster, sections compressing 12.8x, fleet indexes 3.77 GB (certificates three times the estimate because of the kube-root-ca.crt ConfigMap injected into every namespace), ledgers 0.17 GB. The headline holds; the composition shifted from detail to indexes.

Per-cluster keys are about 1.3 to 1.4 MB each, so a single cluster's detail is one round trip of a few hundred KB per section. A single Redis primary with 8 to 16 GB and one replica is enough at 900 clusters; Redis Cluster is not needed for capacity, but the hash-tag layout keeps it possible.

Keyspace at a glance

All keys start with the prefix odl (REDIS_PREFIX). Encoded values are JSON; sections and ledgers are zlib-compressed JSON, with a z: prefix byte marking compression.

Per-cluster keys, hash tag {c:<name>}
KeyTypeContent
odl:{c:<name>}:summaryHASHEvery field of the former clusters row: placement, version, capacity, rollups, health, last_synced, collect_ms, reachable, last_error, hub_name. Scalars as strings, lists and dicts as JSON.
odl:{c:<name>}:sec:<section>STRINGCompressed JSON list of rows for one section. Ten sections: operators, nodes, namespaces, workloads, workload_images, workload_refs, pod_issues, resources, resource_status, health_checks.
odl:{c:<name>}:snapshotsZSETHealth and utilization history. Score is epoch seconds, member is a JSON snapshot. Trimmed to SNAPSHOT_RETENTION.
odl:{c:<name>}:ledgerSTRINGCompressed JSON list of [op, key, member] for every fleet-index member this cluster contributed on its last write. Read and reversed before the next write.
odl:{c:<name>}:lockSTRINGSET NX PX single-flight lock for on-demand refresh of one cluster.

Sections are independent keys, so /api/clusters/{name}/nodes never decompresses the resources section.

Fleet keys, hash tag {fleet}
KeyTypeContent
odl:{fleet}:clustersSETNames of known clusters.
odl:{fleet}:hubsHASHHub name to JSON hub row.
odl:{fleet}:idx:cluster:<dim>:<value>SETCluster names by dimension: region, datacenter, environment, hub, version, status. List filters are SINTER over these.
odl:{fleet}:idx:op:<operator>HASHCluster name to JSON {version, available, progressing, degraded, critical, message}. One HGETALL answers who runs operator X at version Y or degraded.
odl:{fleet}:idx:opsHASHOperator name to refcount. Cleaned of zero counts at sweep end.
odl:{fleet}:nsHASH<cluster>|<namespace> to JSON namespace row, both classes. Feeds applications, blast radius and top-N.
odl:{fleet}:idx:ns:app:<app>SETNamespace members for one application.
odl:{fleet}:idx:ns:team:<team>SETNamespace members for one team.
odl:{fleet}:idx:ns:class:<class>SETNamespace members per class: application, platform.
odl:{fleet}:idx:ns:cpu / :memZSETScore is live usage, member is <cluster>|<namespace>. Top-N namespaces is ZREVRANGE.
odl:{fleet}:nodesHASH<cluster>|<node> to JSON node row.
odl:{fleet}:idx:node:cpu_pct / :mem_pctZSETScore is utilisation percent, member is <cluster>|<node>.
odl:{fleet}:podissues:<class>HASH<cluster>|<namespace>|<pod> to JSON pod issue row, per namespace class. HLEN gives the summary counters.
odl:{fleet}:res:<key>HASH<cluster>|<namespace>|<name> to JSON resource row, for the fleet-indexed kinds only.
odl:{fleet}:res:<key>:status:<status>SETMembers of the hash above with that status. SCARD gives counters; status filters are SMEMBERS plus HMGET.
odl:{fleet}:certsHASHJSON resource row for every certificate-bearing Secret or ConfigMap.
odl:{fleet}:idx:cert:expiresZSETScore is expiry epoch. Expiring-soon is ZRANGEBYSCORE, counters are ZCOUNT.
odl:{fleet}:idx:imagesHASHImage string to fleet-wide refcount. Substring search is HSCAN MATCH *needle*. Zero counts cleaned at sweep end.
odl:{fleet}:idx:image:<sha1>SET<cluster>|<namespace>|<kind>|<workload>|<container> usages of one image.
odl:{fleet}:idx:ref:<kind>:<name>SETWorkloads referencing a Secret, ConfigMap, PVC or ServiceAccount of that name.
odl:{fleet}:runsLISTNewest-first JSON collection runs, trimmed to 200.
odl:{fleet}:run:lastSTRINGJSON of the last run summary: at, ok, trigger.

Fleet-indexed resource kinds: resourcequotas, machineconfigpools, clusterserviceversions, subscriptions, persistentvolumeclaims, persistentvolumes, storageclasses, routes, events, clusterrolebindings. Every other kind is large, rarely queried fleet-wide, and is read only from the per-cluster resources section.

Section

Consequences

Positive

  • No relational database anywhere in the data layer; the deployment is API pods plus Redis.
  • Reads that used to be full-table scans are one pipelined round trip; per-cluster detail is one GET per section.
  • Writes are atomic per cluster and independent across clusters, which is exactly what sharded collectors need (ADR-0003).
  • The cache framing is explicit: TTLs, stale flags and on-demand refresh are first-class instead of implied.
  • The design is portable across managed Redis offerings.

Negative, and the mitigations

  • Ad-hoc queries are not free. Redis answers the questions we indexed; a new fleet-wide question needs either a new index or a scan. ADR-0002 provides the general-purpose query surface, SQL over an embedded snapshot, so that indexes stay small and purpose-built.
  • Hand-maintained indexes are a correctness burden. The ledger makes removal exact, the store tests assert that stale members disappear, and finalize_sweep cleans refcounts. If RediSearch becomes available, the fleet resource hashes and the image and namespace lookups can move to declared indexes with no API change.
  • Filtering happens in process for section reads. A cluster with 16k resources decompresses about 0.5 MB and filters in Python in a few milliseconds. That is acceptable per request and bounded by cluster size, not fleet size.
  • History is capped. SNAPSHOT_RETENTION per cluster (default 500 sweeps) in a ZSET. Longer retention or per-namespace history belongs in the metrics plane or an object-store export, not in Redis.
  • The patching system of record still uses Postgres. It is a separate service with an audit log; moving it needs its own decision, since it is a system of record and not a cache: Redis Streams for the append-only audit, HASHes for jobs, AOF persistence.

Section

Verification

  • Unit tests with fakeredis cover persist, read, re-persist, prune, TTL and retention for every index.
  • End-to-end against the kind fleet: the worktree stack collects the same clusters as the Postgres stack, and the dashboard endpoints return the same structures and counts.
  • A synthetic load test (scripts/synth_load.py) persists 900 generated cluster documents and reports Redis memory, key counts, write throughput and read latency for the fleet endpoints. Its measurements are recorded in ADR-0003.
