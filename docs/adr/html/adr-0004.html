Dashboards from a Question

A question in plain English becomes a multi-panel dashboard, built one validated panel at a time and streamed to the browser as it takes shape. The model composes from the vocabulary the dashboards feature already has; it never writes UI, SQL runs only through the guard, and the result saves like any other dashboard.

Context

The query plane answers one question with one SQL statement (POST /api/query/ask), and a saved dashboard runs many statements against one snapshot (POST /api/dashboards/{id}/run). Neither goes from a question to a view. "What are the apps, namespaces and clusters under hub-east, and how healthy are they" is three or four panels, each a table or a chart, laid out together; today a person writes each panel by hand.

The ask is a mechanism that turns a question written in English into a dashboard with tables and visualizations, built on the fly, that the person can refine in the same conversation. The industry calls this generative UI, and AG-UI (the Agent-User Interaction protocol) is the open event protocol most front-end agent frameworks speak for it.

Generative UI here means composing from a fixed vocabulary of validated parts, never free-form markup from the model. That boundary is what makes the result safe, saveable and reproducible.

Options considered

Five ways to get from a question to a view
OptionWhat it isWhy, or why not
A · one-shot planThe model returns a whole dashboard definition as structured output; the API validates it, runs it, returns itCheapest. No feedback loop: a panel whose SQL fails stays broken, a refinement regenerates everything, and nothing renders until the whole plan is back (20 to 40 s on a six-panel plan).
B · AG-UI agent runA server-side tool-using loop builds the dashboard one validated panel at a time in shared state; every change streams to the browser as an AG-UI event; follow-ups edit the same stateChosen. Progressive, self-correcting, refinable, protocol-standard. More moving parts: a stream, a loop, tool schemas, run limits.
C · CopilotKit end to endCopilotKit's React provider and runtime speaking AG-UI to our agentA large dependency and a second runtime for a chat widget the product does not need. Kept open as a consumer of the same stream.
D · Vercel AI SDK generative UIReact Server Components streaming UI from the modelNeeds Next.js and RSC; the dashboard is a Vite app.
E · MCP Apps / MCP-UITools return UI resources that a chat host rendersA different product: our data inside someone else's chat. Interesting for the MCP server later, not for the in-product dashboard.

Decision

Build option B, as an experiment on its own branch, under five rules.

  1. The shared state is a dashboard definition. The agent's state is {"dashboard": …, "params": …} where dashboard is exactly the shape /api/dashboards saves: a title, variables, and panels that are a query, a chart choice and a size on a 12-column grid. The result saves with the existing PUT, re-runs unchanged, and can be reviewed as plain data.
  2. Every mutation is validated before it becomes state. The model changes the dashboard only through tools. A panel's SQL passes the same guard as every other query and is dry-run against the snapshot; a failure goes back to the model as the tool result and the state does not change. The model never reaches Redis, DuckDB or the file system; the worst outcome of a bad answer is an empty panel.
  3. The wire protocol is AG-UI. The endpoint takes an AG-UI run input (thread, run, messages, state) and answers with a stream of AG-UI events. The browser keeps the thread and sends it back on every follow-up, so the API holds no session and scales like every other endpoint. The events are emitted by a small module of our own rather than the ag-ui-protocol package, which pins pydantic>=2.11 while the service pins 2.10; swapping it in later is a one-file change.
  4. The dashboard renders the state it already knows how to render. A Generate view holds the conversation on one side and the live dashboard on the other. Panels appear as their state delta arrives and run through the existing batch runtime, so a generated dashboard and a saved one are the same components, charts, tables and variable bar. Without credentials, or on an API build without the endpoint, the view says so and nothing else breaks.
  5. Runs are bounded. At most 12 model turns, at most 12 panels, a 150-second wall clock, the existing per-query timeout, and the run stops when the browser disconnects. The model and effort are separate settings from the single-question path, because a composing agent wants a faster model than a one-shot SQL writer may.

How a run flows

The event stream

Each event is one data: {json} frame with a type and the field names the AG-UI specification uses. The order is fixed so a client can hold state without guessing.

Events a run emits, in order
EventFieldsMeaning
RUN_STARTEDthreadId, runIdThe run began; a 503 or 422 would have come before this.
STATE_SNAPSHOTsnapshotThe normalised state the server will mutate; the client replaces its copy.
STEP_STARTED / STEP_FINISHEDstepNameOne model turn.
TEXT_MESSAGE_START / CONTENT / ENDmessageId, role, deltaThe model's narration, streamed as it is written.
TOOL_CALL_START / ARGS / ENDtoolCallId, toolCallName, parentMessageId, deltaA tool call and its arguments as partial JSON; the view already knows the panel's title before it exists.
STATE_DELTAdelta (RFC 6902)Emitted only for an accepted mutation, and always before its result.
TOOL_CALL_RESULTmessageId, toolCallId, content, roleWhat the model sees: columns, a few sample rows and the row count, or the error.
MESSAGES_SNAPSHOTmessagesThe whole thread, so the client can send it back verbatim on the next turn.
RUN_FINISHEDthreadId, runId, resultTurns, tool calls, panels, wall clock and token usage for the run.
RUN_ERRORmessage, codeOne of unavailable, limit, timeout, internal, cancelled; the stream ends.

The final state at RUN_FINISHED equals the snapshot with every delta applied; the tests assert it, and the eval script rebuilds the client's view the same way to prove the two agree.

The tools

What the model may do, and what refuses it
ToolEffectRefused when
preview_sqlRuns a query and returns up to ten rows; changes nothingThe guard rejects it, DuckDB cannot run it, or a variable it uses is unset
set_dashboardSets the title, and the description when givenThe title is blank
add_panelDry-runs the SQL, then appends a panel with a chart choice (auto, line, bars, none), axes and a sizeThe dry run fails, the panel cap is reached, or the whole definition no longer validates
update_panelReplaces a panel by id after dry-running its effective SQLUnknown id, or the same reasons as add_panel
remove_panelRemoves a panel by idUnknown id
add_variableAdds a select, text or number input; a select's options query is dry-run; a default also sets the parameterThe options query fails or uses a variable, or the name is not a placeholder name

Tool argument errors (a missing field, a wrong type) come back as tool results too, never as exceptions, so the model can correct itself within the run.

What was built

Data layer

  • app/agent/: config (limits), events (the fifteen AG-UI builders and SSE framing), state (the empty dashboard and an all-or-nothing JSON Patch applier), tools (six tools with pydantic argument models, dry run before every mutation, whole-definition re-validation), messages (AG-UI to Anthropic and back), prompt (a cached system block with the schema and composition rules; live fleet values prepended to the last user turn as data), model (the streaming Anthropic adapter behind a seam tests replace), run (the loop).
  • app/api/agent.py: GET /api/agent for availability and limits, POST /api/agent/run streaming from a worker thread through a queue, cancelled when the client disconnects.
  • scripts/eval_generate.py: runs the golden questions against a live API, rebuilds the client's state from the stream, re-runs the finished definition through the batch endpoint and prints turns, tool calls, panels, errors, wall clock and tokens.
  • 84 tests: event field names and framing, the patch applier, every tool's success and refusal paths, event order, snapshot plus deltas equals final state, thread round-trip, turn and time limits, cancellation, and the endpoint's 503, 422 and full stream.
  • The credential check moved to client construction, so GET /api/agent and /api/query/ask report "unavailable" on a box with no key instead of every run ending in an error.
  • The container's nginx streams /api/agent/ unbuffered.

Dashboard

  • src/agent/: client (a fetch-and-ReadableStream reader for server-sent events, the JSON Patch applier), useAgentRun (the thread, the state, a transcript of narration and tool activity, stop and reset, persistence in session storage so reload and back/forward keep the conversation), fixture (a scripted stream for development without credentials).
  • views/Generate.jsx at /generate: the conversation on the left with examples and a composer, the live dashboard on the right using the dashboards page's own variable bar, grid and panels. A panel being added shows as a placeholder whose title assembles from the streaming arguments; a panel being updated dims until its delta lands; panels run through the batch runtime as the state changes. "Save as dashboard" writes the definition through the existing PUT and opens it in the Dashboards tab.
  • Entry points: "Generate from a question" on the Dashboards list, and "Build a dashboard from this question" under the Query page's ask box, which carries the question in ?q=.
  • Degrades in place: an API without the endpoint, or without credentials, gets a banner with the reason and the rest of the application is untouched.

Consequences

  • A question becomes a dashboard in one conversation, and the person can say "make the second one a bar chart" or "add pending pods per namespace" without starting over.
  • The same stream can drive any AG-UI client (CopilotKit, a chat host, a terminal); the dashboard is not the only consumer.
  • A generation costs one model turn per tool call plus one per narration, roughly 6 to 12 calls for a five-panel dashboard; the eval records the numbers the model choice should rest on.
  • The dashboards contract (definition shape, guard, batch runtime) is now load-bearing for two features; the shared tests keep both honest.
  • Nothing in the existing product changes: the endpoint and the view are additive, and the branch stays an experiment until the numbers say it should merge.
