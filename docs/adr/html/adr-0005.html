Dashboard to TypeScript and MUI

The dashboard is 11,000 lines of plain JavaScript with two dependencies and a hand-rolled design system. It moves to TypeScript first, so the API boundary is checked, and to Material UI second, so the component swap is typed and reviewable. Six phases, each landing only when the type check, the 896 tests and the build all pass.

Where it stands

The dashboard runs on React 18 and Vite 6 with exactly two runtime dependencies. Everything else was written here: a History API router, an SWR-style fetch cache, a DataTable used 57 times across 11 files, a 1,183-line SVG Chart that infers axes and series from a result's columns, and a 790-line stylesheet with 31 tokens and 183 classes. There are no types. The API contract exists as the fetch helpers and as the test fixtures that imitate the endpoints.

Two integration bugs this month were shape mismatches at that boundary: a blank dashboard title the API rejected, and a pod identity the collector discarded. A type checker at the boundary would have caught both.

TypeScript first, Material UI second: typed props make the component swap mechanical, and swapping first would mean typing everything twice.

Decision

  1. Incremental, on one branch, with the tests as the net. allowJs lets .js and .tsx coexist, so no phase leaves the branch unable to build, test and pass the 70% floor.
  2. One source for the API contract. Request paths, parameters and bodies are generated from the data layer's OpenAPI document. Responses are typed by hand because no route declares a response model; the fixtures are typed with those interfaces so drift fails the type check.
  3. Strict is the end state. Phase 1 converts loosely; Phase 2 turns strict on and clears what it finds. The type check joins CI as soon as Phase 1 lands.
  4. MUI replaces the design system, not the architecture. Router, cache, API layer, query builder, dashboards runtime and the agent stream client stay. The theme is built from the existing tokens, which yields the light theme the app never had.
  5. Free tiers of MUI X. DataGrid does sorting, single filters, quick search and paging; today's per-column filter row survives by filtering rows before the grid. Charts covers line and bar with tooltips and legends. Pinning, grouping and multi-filter panels are paid features and are not in scope.
  6. React 19 only on purpose. Material UI 9's peer dependencies are checked before anything is installed; a React upgrade is a recorded decision inside Phase 3, not a side effect.

Risks and how each is held

  • A phase that half-lands. Every phase is one commit that passes type check, tests at the floor and build; the reviewer runs the gate before committing, and a phase that cannot pass is not committed.
  • Two workers editing one file. Phase 2 splits by file ownership and forbids renaming exports; Phases 3, 4 and 5 own disjoint files and share only theme.ts, which lands first.
  • Tests that assert on class names. Sixty-nine of them; they are rewritten to roles and text as the components change, never deleted.
  • MUI 9 and React 18. Peer dependencies decide; a React 19 upgrade, if needed, is made and tested inside Phase 3 and recorded.
  • Bundle growth. Several hundred kilobytes gzipped; measured before and after each phase and recorded below; acceptable for an internal tool served same-origin.
  • Paid MUI X features. None used; the wrapper keeps today's multi-column filtering outside the grid. Pro is a later choice, not a dependency of this plan.

Measured

Filled in as each phase lands.

The backend now marks the two free-form params bodies as open objects so the generated request types accept keys.
